# Failure Story: AWS S3 us-east-1 (February 2017)

## What happened

An AWS engineer ran a command to remove a small number of servers from an S3 index subsystem. The command was entered incorrectly and removed a much larger set of servers than intended. Two of those subsystems — the index and the placement — were critical to S3's operation. With them down, S3 could not serve requests in us-east-1.

The impact cascaded far beyond S3 itself. Hundreds of services that depended on S3 (or on other AWS services that depended on S3) broke or degraded. EC2 instances couldn't launch, Lambda functions failed, Docker Hub couldn't pull images, and many websites went dark. The outage lasted several hours.

## Why it was so severe

- **Single point of failure:** S3's index and placement subsystems had no redundancy within the region at the level that mattered.
- **Hard dependency:** Many downstream services treated S3 as a hard requirement rather than an optional cache. When S3 was slow or unavailable, they failed instead of degrading gracefully.
- **No circuit breaker:** Callers kept retrying against an unresponsive dependency, amplifying load on recovery and tying up connection pools.
- **Recovery was slow:** S3 subsystems had to be restarted slowly to avoid overwhelming them, extending the outage.

## The system-design lesson

**Never treat an external dependency as infinitely available.** Every call to another service should assume it can fail or be slow, and the system should degrade gracefully rather than collapse.

Specifically:
- **Circuit breakers:** Stop calling a failing dependency for a cooldown period instead of retrying endlessly. See [module 05](../05-reliability-and-protection.md).
- **Graceful degradation:** Serve cached or partial results instead of erroring when a non-critical dependency is down.
- **Fail-open vs fail-closed:** Decide per API whether unavailability of a dependency should block the request or let it proceed with reduced functionality.
- **Multi-region / multi-AZ:** Critical dependencies should be redundant across availability zones and, for truly critical workloads, across regions.

## Interview angle

If an interviewer asks "how do you make this design reliable?" you can say:

> "I'd add a circuit breaker in front of any external dependency so a slow or down service doesn't take down our callers. For non-critical data like thumbnails or analytics, I'd fail open and serve stale or partial results. For critical data like payments, I'd fail closed and return an error rather than risk inconsistency."
